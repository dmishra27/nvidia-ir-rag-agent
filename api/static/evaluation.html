1Method comparison — BM25 vs dense vs RRF

15 queries across 6 cases, each designed to probe a structural strength or weakness of one retrieval method, run live against the 5,389-chunk corpus (docs/uat/uat_superiority_cases_raw.json / uat_superiority_cases_executed.md). This pool is referred to here as the Round 2 method-comparison set.

Headline finding: BM25 wins on exact terminology (rare API symbols like cudaMalloc, cudaErrorInvalidValue, struct field names), dense wins on semantic phrasing (queries that paraphrase rather than quote the source text), and RRF wins or ties on mixed queries where both a lexical and a semantic signal are present. No single method dominates end to end.

The case hypotheses held in 10 of 15 queries. Two flipped outright: Q2 was designed to showcase BM25 but RRF's pool corroboration found the best chunk instead, and Q12 was designed as a BM25 "exact lookup" case but dense won cleanly — term-frequency dilution across many API chunks sharing the literal string cudaDeviceSynchronize hurt BM25 more than semantic similarity hurt dense.

3RAGAS faithfulness

A live RAGAS run over 10 real QA-agent outputs measured faithfulness: 0.7616 — how well each generated claim is actually supported by its retrieved passages (logged to MLflow experiment ragas_eval, run 7d8f1005).

This is an automated, LLM-judged score of groundedness, not a human judgement of answer quality. No human evaluation of the QA agent's answers has been performed yet — faithfulness tells you the model isn't hallucinating relative to what it retrieved, not that what it retrieved (or answered) was actually the right thing to say.

Source: docs/daily_progress/day_11_storyline.md (§3, RAGAS live run results table).

4Architectural findings

RRF's corroboration bias

Reciprocal rank fusion rewards candidates two signals agree on, even moderately, over a candidate either signal ranks highly alone. Measured directly on Q1 (BM25 + dense, top_k=100 each, RRF k=60): the chunk containing the actual cudaMalloc(void **devPtr, size_t size) signature with both parameters named ranked BM25 #2 (score 11.99) and dense #75 (cosine 0.872) — strong on one signal, weak on the other — yet fused to only rank 4 (RRF 0.0235). Fused rank 1 went instead to 81b9c458…, a chunk about cudaFreeArray that mentions cudaMalloc only in a "see also" list (RRF 0.0317) — it sat at rank 3 in both input lists. Two-list moderate agreement outscored one-list strong confidence, the same pattern already documented on Q10 above.

A cross-encoder that scores each candidate independently — rather than by rank position — was expected not to be subject to this mechanism. Re-ranking the fused top-10 with the ms-marco cross-encoder confirms the independence claim on its own terms: chunks with weak fused support (fused ranks 8 and 10) rose to CE ranks 3 and 4, while chunks with strong two-list fused support (fused ranks 2 and 3) fell to CE ranks 5 and 7 — rank agreement clearly isn't what the cross-encoder is scoring. But it does not confirm the expected outcome: the cross-encoder still placed the cudaFreeArray chunk first (CE rank 1, score 6.0145), ahead of the actual signature chunk (CE rank 2, score 5.4647). Corroboration bias isn't the mechanism — the cross-encoder never saw rank positions, only text — yet the same wrong chunk won under both mechanisms. Both retrieval strategies failed on this input, for different reasons.

Root cause: chunk boundaries straddle API entries

Inspecting the text of the chunks that dominate Q1's pool explains why. All four come from the same source, the CUDA Runtime API Reference, and three of them — the CE rank 1 chunk (cudaFreeArray), the CE rank 3 chunk (cudaGraphMemAllocNodeGetParams), and the CE rank 8 chunk (cudaLaunchKernelEx) — open with the identical verbatim sentence "Note that as specified by cudaStreamAddCallback no CUDA function may be called from callback," followed by a "Parameters" block belonging to a different function entirely. The chunker is producing chunks shaped like trailing boilerplate from one API entry + header of the next, and that boilerplate happens to contain "CUDA", "function", and "Parameters" — the exact vocabulary shape of the query. Every retrieval method scores these chunks highly because those tokens are genuinely present in the text, not because of a bug in any ranking strategy. This is a corpus-quality defect, not a ranking defect: no fusion method or reranker can fix it by scoring better, because the offending chunks really are lexically and semantically similar to the query. The remedy is chunk-boundary alignment to function-entry boundaries at ingestion time, not filtering or re-ranking after the fact.

Source: live measurement against the running bm25_index.pkl and nvidia_ir_chunks Qdrant collection this session (retrieval/bm25_index.py, retrieval/dense_index.py, retrieval/rrf_fusion.py, retrieval/reranker_msmarco.py), chunk text and section headings read from chunks / doc_metadata in Postgres — not yet snapshotted to a committed artifact file.

5What fusion does to a good result

§4 examined RRF's behaviour on Q1 in detail. The same rank-only mechanism cuts both ways across the wider query set — sometimes lifting a chunk one retriever missed, sometimes burying one only a single retriever found. The five queries below were re-measured live (BM25 + dense top-100 each, RRF k=60) for the D-QR evaluation; ranks are the target chunk's position in each list.

QueryBM25DenseRRFEffect
R1-Q7 · shader processor countnot in top 100110fusion demotes
Q10 · latency hiding through instruction level parallelismweak (14)14fusion demotes
Q11 · occupancy versus performance tradeoffsweak (6)14fusion demotes

Q3 · CUDA error cudaErrorInvalidValue descriptionstrong (1)492fusion rescues

RRF scores a chunk on its rank position in each list — 1/(60 + rank) summed across retrievers — and never on how confident either retriever was. A chunk that one retriever is uniquely right about carries a single such contribution, and a single contribution loses to chunks that both retrievers rank only moderately: two mid-table agreements outscore one strong solo hit.

That arithmetic rescues queries where one retriever is lost — on Q1 dense buries the cudaMalloc signature at rank 75, BM25 holds it at rank 2, and the sum lands it at fused rank 4 (§4 covers why fusion still didn't restore it all the way to rank 1 — a straddling-boilerplate chunk beat it there); Q3 is the same shape, dense rank 49 lifted to fused rank 2. It penalises queries where one retriever is uniquely correct — on R1-Q7 (shader processor count), Q10 and Q11, dense ranks the right chunk #1 and BM25 does not corroborate it, so fusion pushes it down to ranks 10, 4 and 4. R1-Q7 is the sharpest case: dense is right, BM25 never surfaces the chunk at all, and after cross-encoder re-ranking the chunk drops out of the top 10 entirely — which is why /search returns nothing useful for that query under live_fast.

The pattern: fusion is a net positive when neither retriever can be trusted alone, and a net negative when one retriever is decisively correct and the other is silent. RRF cannot tell those two situations apart, because it has discarded the score information that would distinguish them.

Query rewriting (D-QR) — evaluated, not shipped

A conditional query-rewriting step (retrieval/query_rewrite.py) was implemented and evaluated against 16 queries in three arms — baseline, gated (skip exact-identifier lookups), and ungated — to see whether expanding legacy terminology on the dense query could close gaps like R1-Q7's. It was deliberately not wired into retrieval. The measured reason: the rewrite moved the target chunk's dense rank on exactly one of the 16 queries (Q4, 16 → 10), and fusion then absorbed half of even that gain; the identifier gate's net effect across all 16 queries is zero. R1-Q7 specifically is unreachable by rewriting — the expansion touches only the dense query, and the bridging term CUDA is too frequent in the corpus to carry weight in BM25 anyway. The bottleneck there is fusion, not vocabulary.

Not a live feature. /search and /ask do not rewrite queries. Full write-up, per-query table, and three-arm comparison: docs/uat/round3_dqr_findings.md (raw data: evaluation/dqr_eval.json).

6Limitations

  1. Smoke-scope benchmark. The NDCG@10 gate above runs over 15 queries × top-3 RRF candidates, not the full 50-query × top-100 evaluation benchmark_runner.py is designed for — still an open item.
  2. Config B never ran. bge-reranker-v2-m3 is hardware-blocked on this project's CPU-only 8GB dev machine; there is no live number for it, and none should be assumed.
  3. No human answer-quality judgement. RAGAS faithfulness (0.7616) is an LLM-judged, automated proxy over only 10 QA outputs — no human has reviewed the agent's answers for correctness or usefulness.
  4. NDCG here is an upper bound, not a production estimate. The live Qdrant collection holds 5,389 points — below Qdrant's HNSW indexing threshold — so dense retrieval during evaluation ran as exact/exhaustive search rather than the approximate HNSW search a production-scale collection would use. Exhaustive search never makes a worse ranking decision than an approximate index would; every NDCG figure on this page is therefore an upper bound on what a larger, HNSW-indexed collection would score, not a number that generalizes as-is.

Evaluation figures are read from committed, live-measured artifacts — no numbers on this page are estimated or simulated.
